# Verified SQL Data Factory — detailed handoff context

## 1. What this project is

This repository is building a **verification-first synthetic SQL dataset factory**. It is not merely asking a language model to write SQL and saving the answer. Its intended product is a dataset of SQL tasks and SQL answers where every accepted answer has execution and independent correctness evidence.

The target users are teams building or evaluating SQL agents, data agents, coding assistants, and model-training systems. The business hypothesis remains **INSUFFICIENT_EVIDENCE**: the technical pipeline exists, but no real training experiment, customer sale, or measured model improvement has been claimed.

### Small glossary

- **Database (DB):** an organized collection of data. In this project, each task creates a small synthetic DuckDB database with tables such as `customers`, `orders`, and `events`.
- **SQL (Structured Query Language):** the language used to ask questions of a database, such as “total sales per month.”
- **Table:** data arranged in rows and columns, like a spreadsheet.
- **Schema:** the table design: table names, column names, types, and whether a column may be empty.
- **DuckDB:** the SQL database engine used by the sandbox and the task contracts.
- **Candidate:** one SQL answer generated by the model for one task. Three candidates are requested per task in the qualification runs.
- **Oracle:** independent Python code that computes the correct result directly from the task data. It is not model output and is not the candidate SQL.
- **Golden record:** a candidate that passes execution, independent verification, quality gates, contamination checks, duplicate rules, and any required audit policy. A PASS is necessary but not automatically Golden.

## 2. The pipeline

```text
Versioned task template + deterministic seed
  -> TaskInstance: instruction, schema, fixture data, requirements
  -> Devstral generates three candidate SQL answers
  -> security gate + isolated Docker/DuckDB sandbox executes each answer
  -> independent oracle, hidden fixtures, properties, metamorphic checks, mutations
  -> PASS / FAIL / INCONCLUSIVE
  -> quality, duplicate, diversity, contamination, audit selection
  -> Golden / excluded / inconclusive / audit-required evidence
  -> later: provenance snapshot, product release, private benchmark
```

Every stage preserves its artifacts. Failed model outputs are evidence; they are not deleted to make results look better.

## 3. Why the stages exist

### Task Engine

YAML templates in `templates/sql/` describe each task. A deterministic seed creates the same fixture data and task identity every time for the same template version and config. There are ten SQL families: simple joins, multi-table joins, aggregation, CTE, subqueries, window functions, temporal analysis, deduplication, retention, and funnel analysis.

### Generation

The selected model is:

```text
alibilge/Huihui-Devstral-Small-2-24B-Instruct-2512-abliterated:latest
revision: ollama-digest:a2d26ea0b96b7a40afd673158d5cf44de25eff07fc8abf835e2cde5444632bc4
endpoint: http://localhost:11434/v1
prompt version: sql-v2
temperature: 0.4
top-p: 0.95
max tokens: 2048
```

The model is only a generator. It does not decide whether its answer is correct.

### Secure execution

Candidate SQL is treated as untrusted. It runs in an isolated Docker sandbox with network disabled, non-root execution, read-only root filesystem, restricted resources, single-statement policy, and result-size limits. Execution success means only “DuckDB ran this SQL”; it does not mean the SQL is correct.

### Independent verification

The verifier compares the candidate output with the independent oracle and also runs:

1. **Main result comparison:** exact required columns, rows, values, and order where order matters.
2. **Hidden fixtures:** new seeded data not shown in the public task fixture. This detects SQL that accidentally fits only one dataset.
3. **Property tests:** invariants that must hold, such as row-order invariance.
4. **Metamorphic tests:** controlled input changes that should preserve or predictably change a correct answer.
5. **Mutation tests:** deliberately wrong variants of the candidate SQL, such as `SUM -> AVG`, dropped filters, flipped order, or changed window partition. A good suite must kill these mutants.

The verdicts are:

- **PASS:** candidate satisfies every mandatory check and suite strength is sufficient.
- **FAIL:** the candidate demonstrably violates the contract, for example a result mismatch or execution error.
- **INCONCLUSIVE:** correctness cannot be established safely. A weak mutation suite yields INCONCLUSIVE, not PASS and not FAIL.

The mutation threshold remains **0.90**. It was never lowered.

### Quality and Golden selection

Phase 5 examines verified records for exact, structural, and semantic duplicates; task quality; coverage; contamination; diversity; difficulty; and deterministic audit sampling. This is why Golden counts are lower than PASS counts. For example, many syntactically different SQL answers can be semantically the same answer to the same task; only a representative is retained.

## 5. CTE, temporal, and window repair history

### CTE

The original failures included unsupported `DATE_FORMAT`/`TO_CHAR` use, reversed `strftime` arguments, and query shapes that joined a monthly aggregate back to a second copy and duplicated results.

CTE v4 now explicitly requires DuckDB’s `strftime('%Y-%m', CAST(order_date AS DATE))`, says the format string is first, forbids applying `strftime` again to an already formatted month string, and requires ranking/filtering the same monthly CTE rather than rejoining it.

The remaining issue was **test-suite strength**, not an oracle error. Some generated fixtures made `SUM(amount)` and `AVG(amount)` observationally equivalent for the selected top month. A mutation-only fixture now inserts two unequal qualifying orders in the same customer/month and makes that month dominant. This leaves the original task fixture, oracle, threshold, and candidate contract unchanged. Focused real-Docker tests confirm `SUM -> AVG` is killed.

### Temporal

The v3 failures were mostly execution problems: `DATE_FORMAT`, `TO_CHAR`, reversed or ambiguous `strftime`, ambiguous `activity_month`, undefined `event_count`, and incorrect raw-table joins.

Temporal v4 fixed those dialect and alias failures by defining DuckDB expressions, separate monthly CTEs, qualified aliases, and a final FULL OUTER JOIN over already aggregated months. However, the phrase “include both ends of the window” was too easy for the model to omit. Twenty-three candidates generated the correct-looking aggregation shape but no date filter, returning 11–12 months instead of the required January–March three-month window.

Temporal v5 is a narrow versioned repair. It names and repeats the two exact mandatory predicates:

```sql
-- orders_by_month
WHERE order_date >= DATE '2025-01-01'
  AND order_date < DATE '2025-04-01'

-- events_by_month
WHERE event_time >= TIMESTAMP '2025-01-01 00:00:00'
  AND event_time < TIMESTAMP '2025-04-01 00:00:00'
```

The exclusive April 1 upper bound includes every timestamp on March 31, unlike a naive `<= DATE '2025-03-31'` timestamp comparison. The v5 requirement fields are deterministic and task-versioned. The oracle was not changed.

### Window functions

The window task asks for rank and running totals partitioned by customer. The original mutation suite could select an unsuitable partition-replacement column or use a fixture where changing the partition had no observable effect. The corrected harness resolves a replacement column from the actual table alias and uses a mutation-only fixture that forces two qualifying customers into a shared country with distinct amounts. The partition-column-swap mutant now dies with `result-mismatch`; score is 1.00 in focused real-Docker tests and all completed qualification results.
